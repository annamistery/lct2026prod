# Алгоритм цифрового сомелье

Как сомелье подбирает вина к блюдам, что он говорит о распознанном вине и где в этом участвует LLM.
Описание составлено по коду `app/sommelier/` (состояние на 17.10.2026). API и настройки описаны в [`SOMMELIER.md`](SOMMELIER.md),
устройство модуля — в [`app/sommelier/README.md`](../app/sommelier/README.md).

## Общие принципы

- **Решает движок, LLM только формулирует.** Какие вина показать, их баллы, роли, доводы и оговорки считает движок
  по явным формулам. Необязательный LLM-слой (`llm.py`, Google Gemini) пересказывает готовый ответ движка живым языком
  и отвечает на общие вопросы о вине. Выбор вин и факты он не меняет.
- **Без LLM всё работает.** Если `GOOGLE_API_KEY` не задан, ответы собираются по шаблонам (`explain.py`). Если ключ задан,
  но LLM ошиблась, не уложилась в таймаут или её ответ не прошёл проверки, гость получает тот же шаблонный текст.
- **Только факты из карточки.** Все признаки вина берутся из названия, slug и описания. Если признака в тексте нет,
  он остаётся пустым («в базе не указано»), а правило, которому он нужен, не даёт баллов. LLM получает те же данные
  и не может добавлять своих фактов о конкретных винах.
- **Свой каталог.** Сомелье читает `app/sommelier/data/wines_integrated.csv` (2108 вин) один раз при старте API.
  С базой распознавания (PostgreSQL) этот каталог не связан. Вино, добавленное в базу распознавания,
  нужно отдельно добавить в CSV и перезапустить API.

| Файл | Роль |
|---|---|
| `catalog.py` | загрузка CSV, чистка сортов, сборка каталога |
| `features.py` | извлечение признаков вина из текста |
| `dishes.py` | разбор блюда по вкусовым осям |
| `context.py` | разбор запроса гостя: блюдо, цвет, сладость, сорта, повод |
| `engine.py` | фильтры, скоринг, выбор разных вин, альтернативы, профили сортов и типов |
| `explain.py` | шаблонные тексты объяснений, структурированная карточка вина |
| `guardrails.py` | этические ограничения, проверка тона, нейтральные пометки |
| `llm.py`, `SYSTEM_PROMPT.md` | необязательный LLM-слой и его системный промпт |
| `sommelier.py` | диалог, определение типа запроса, точки входа |

## Маршрут сообщения в диалоге

Точка входа: `POST /api/sommelier/ask` (диалог с сессией). Сообщение проходит шаги по порядку,
первый сработавший определяет ответ (`kind`):

| № | Проверка | Ответ | LLM |
|---|---|---|---|
| 1 | этические ограничения (`guardrails.check`) | `guardrail`, готовый текст отказа | нет |
| 2 | оценка прошлой выдачи («не понравилось 2», «беру») | `feedback` | нет |
| 3 | «этикетка», «на фото», «распознан» + название вина из каталога | `wine_info`, справка по вину | нет |
| 4 | «чем отличается», «сравни», «или» + два сорта или типа, без блюда | `comparison`, сравнение групп | пересказ (`retell`) |
| 5 | «расскажи», «что такое», «опиши» + сорт или тип, без блюда | `profile`, профиль группы | пересказ (`retell`) |
| 6 | в сообщении нет ни блюда, ни повода, ни пожеланий | `answer` — свободный ответ LLM; без LLM или при сбое — `clarify`, уточняющий вопрос | ответ (`answer`) |
| 7 | всё остальное | `recommendation`, подбор вин | пересказ (`polish`) |

Шаг 6 срабатывает и посреди диалога: на вопрос «а при какой температуре его подавать?» LLM отвечает с учётом
контекста сессии (блюдо гостя и названия вин последней выдачи). Без LLM, если блюдо уже известно, сообщение
дополняет прежний запрос и сомелье заново выдаёт подбор.

## Шаг 0. Признаки вина

При старте для каждого вина из текста извлекаются признаки (`features.py`).

| Признак | Шкала | Как определяется |
|---|---|---|
| Сладость | 0 сухое / брют, 1 полусухое, 2 полусладкое, 3 сладкое | по порядку: название → slug (`suhoe`, `polusladkoe`…) → фраза в описании («полусладкое белое вино») |
| Игристое | да / нет | слова «игрист», «брют», «шампанск», «петнат», «перляж» и т.п. |
| Кислотность | 1 / 2 / 3,5 | прилагательное в пределах ±28 символов от «кислотн»: «мягкая» → 1, «умеренная» → 2, «яркая», «свежая» → 3,5 |
| Танины | 1 / 2 / 3,5 | то же рядом с «танин»: «бархатистые» → 1, «сбалансированные» → 2, «выраженные», «терпкие» → 3,5 |
| Тело | 0,5–4 | от базы 2,5: «лёгкое», «питкое» −0,8; «изящное», «освежающее» −0,3; «плотное», «мощное» +1,0; «насыщенное», «глубокое» +0,4; поправки на танины и выдержку в дубе от 6 месяцев |
| Дуб, выдержка | да / нет, месяцы | «дуб», «бочка», «баррик», «ваниль», «тост»; число месяцев или лет выдержки |
| Ароматы | 19 групп | красные и тёмные ягоды, цитрус, косточковые, тропические, цветы, травы, пряности, дуб, шоколад, мёд, минеральность, землистые, орехи, сухофрукты, выпечка, мускат, дым и др. |
| Блюда из описания | 10 категорий | предложения со словом-маркером («подавать», «сочетается», «к мясу») и категорией еды: красное мясо, птица, свинина, рыба, морепродукты, сыр, десерт, закуски, паста/пицца, овощи, острое/азиатское, аперитив |
| Температура подачи, крепость | °C, % | «15–18°», «крепость 14%» |

У каждого найденного признака хранится цитата-доказательство, которая потом попадает в ответ гостю.

Полнота данных по каталогу: сладость 78 %, тело 77 %, кислотность 47 %, танины 24 %, выдержка 7 %.

## Блюдо → вино

### 1. Разбор запроса

Запрос разбирается правилами (`dishes.py`, `context.py`). LLM в разборе не участвует: метод `extract_context`
в `llm.py` есть, но не подключён.

**Блюдо раскладывается на шесть осей** (`dishes.py`):

| Ось | Шкала | Смысл |
|---|---|---|
| intensity | 0–4 | «громкость» блюда |
| fat | 0–4 | жирность |
| acid | 0–4 | кислотность |
| sweet | 0–3 | сладость |
| salt | 0–4 | солёность |
| heat | 0–4 | острота |

- **Основа блюда** ищется по словарю из 35 позиций: стейк, баранина, шашлык, утка, рыба, сыры, десерты и т.д.
  Например, «утка» задаёт интенсивность 3,0, жир 3,5, соль 1,5. При нескольких совпадениях по каждой оси берётся максимум.
- **Модификаторы** (соус, способ приготовления) поднимают оси и сдвигают интенсивность:
  «вишнёвый соус» → сладость 1,0, кислота 1,5, тег «сладко-кислый»; «острый» → острота 3;
  «на гриле» → интенсивность +0,4; «на пару» → −0,3. Итоговый сдвиг интенсивности ограничен диапазоном от −0,5 до +0,9.
- **Теги** нужны правилам аромата: «красное мясо», «рыба», «грибы», «десерт», «острое»…
- Дополнительно определяются регион кухни (Кубань, Крым, Дон, Дагестан…), стиль кухни
  (кавказская, средиземноморская, азиатская) и курс (аперитив, закуска, основное, десерт).

**Пожелания гостя** (`context.py`): цвет, игристое или тихое, сладость, любимые и нелюбимые сорта,
отношение к дубу, танинам и телу, регион, повод (праздник, аперитив, свидание, деловая встреча, подарок,
семья, просто так), уровень гостя (новичок или знаток). Бюджет запоминается, но не применяется: цен в каталоге нет.

### 2. Жёсткие фильтры

Отсекаются вина:

- отвергнутые гостем в этой сессии;
- другого цвета, если цвет задан;
- игристые или тихие вопреки запросу;
- с другой сладостью (если сладость вина известна);
- с нелюбимым сортом;
- с дубом, если гость просил без дуба.

### 3. Скоринг по восьми правилам

Каждое правило даёт вклад v от −1 до +1, вклад умножается на вес правила.

| Правило | Вес | Когда применяется | Формула и логика |
|---|---|---|---|
| Вес блюда ↔ тело вина | 3,0 | всегда при блюде | v = 1 − 2·\|intensity − тело\| / 3 |
| Кислотность режет жир | 2,0 | жир ≥ 2 | v = (жир / 4)·(кислотность − 2) / 1,5 |
| Сладость | 3,5 | всегда при блюде | см. ниже |
| Танины | 2,5 | жир ≥ 2,5, или острота ≥ 1,2, или соль ≥ 2,5 | см. ниже |
| Регион | 1,0 | у блюда определён регион | +1, если регион кухни совпадает с регионом вина |
| Аромат | 1,5 | у блюда есть теги со связками | +0,8 за дополнение, +0,6 за контраст, +1,0 если описание вина само называет такую категорию блюд |
| Повод | 1,2 | повод назван | праздник → игристое +0,7; аперитив → игристое или лёгкое белое +0,7, плотное −0,5; деловая встреча → классический сорт +0,5; свидание, подарок → игристое +0,3 |
| Предпочтения | 2,5 | гость назвал сорт, регион, танины или тело | любимый сорт +0,8; регион +0,4; танины по вкусу +0,5 / −0,3…−0,4; тело по вкусу до +0,6 |

**Сладость.** ds — сладость блюда, ws — сладость вина. Допуск: 0 к десертам и фруктам, 0,6 к остальным блюдам.

| Ситуация | Вклад |
|---|---|
| вино суше блюда больше допуска | −min(1; (ds − ws − допуск) / 1,5) |
| блюдо сладкое (ds ≥ 1), вино не суше | +0,5 (+0,2, если вино слаще больше чем на ступень) |
| острое блюдо или сыр с плесенью / печень, вино полусухое или полусладкое | +0,6, контраст |
| сладкое вино к несладкому блюду (кроме аперитива и десерта) | −0,2·ws |
| сухое вино к несладкому блюду | +0,4 (полусухое +0,2) |
| сладость вина неизвестна, блюдо сладкое | −0,3 |

**Танины** (t — уровень танинов вина):

- «жгучесть» блюда h = max(острота / 4; (соль − 1,5) / 2,5);
- штраф, если t ≥ 2 и h > 0,2: −min(1; (t − 1) / 2,5 · h · 1,6) — танины конфликтуют с солью и острым;
- бонус, если t ≥ 2 и блюдо жирное (жир ≥ 2,5, или красное мясо / сыр при жире ≥ 2):
  +0,6·min(1; t / 3,5)·min(1; жир / 3) — танины связываются с белком и жиром;
- если у красного вина танины не указаны, берётся медиана по красным винам каталога, а вклад делится пополам.

**Связки по аромату** (дополнение / контраст):

| Тег блюда | Дополнение | Контраст |
|---|---|---|
| грибы | землистые, орехи | — |
| баранина | травы, пряности | — |
| красное мясо, гриль | дым, пряности, тёмные ягоды | — |
| утка | красные ягоды | — |
| сладко-кислый соус | красные и тёмные ягоды | — |
| морепродукты, рыба | минеральность | цитрус |
| сыр с плесенью | — | мёд, сухофрукты |
| десерт | косточковые, мёд, тропические, сухофрукты, красные ягоды | — |
| шоколад | шоколад/кофе, тёмные ягоды, сухофрукты | — |
| овощи | травы | цитрус |
| острое | — | тропические, косточковые, цветы |

### 4. Итоговый балл

```
балл = 50 + 50 · Σ(вес · v) / max(P; 3)
```

P — сумма весов правил, **применимых к запросу** (не к данным о вине). Если о вине чего-то не известно,
правило даёт 0, но его вес остаётся в P. Поэтому вино с подтверждёнными признаками обходит вино,
о котором база молчит. Балл ограничен диапазоном 0–100.

### 5. Выбор трёх разных вин

1. Вина сортируются по баллу; одноимённые (разные урожаи) оставляются по одному; берутся первые 120.
2. Первым идёт лучшее по баллу.
3. Следующие вина выбираются среди тех, что отстают от лучшего не больше чем на 15 баллов,
   по максимуму величины `балл − 25 · похожесть на уже выбранные`.
   Похожесть: тот же сорт 0,4; тот же цвет и игристость 0,3; тот же регион 0,15; та же винодельня 0,15.
4. Роли:
   - «Лучшее совпадение по правилам» — первое вино;
   - «Классический вариант» — сорт входит в 15 % самых частых в каталоге;
   - «Нестандартный выбор» — редкий сорт (не больше 8 вин в каталоге);
   - «Другой стиль для сравнения» — остальное.

### 6. Уместность типов вина

Вина группируются по цвету, игристости и сладости; учитываются группы, где не меньше 5 вин.
Для группы считается средний балл пяти лучших вин и главная причина «за» и «против».

| Отставание от лучшей группы | Вердикт |
|---|---|
| до 6 баллов | подходит |
| до 14 баллов | допустимо, с оговорками |
| больше 14 | лучше избегать |
| сильный штраф за сладость (сумма < −1) | лучше избегать |

### 7. Шаблонный ответ

`explain.py` собирает текст для каждого вина: роль, тип и сорт, доводы из сработавших правил с цитатами из описания,
оговорки (отрицательные правила), список «в базе не указано», ссылка на карточку. Глубина подачи зависит
от уровня гостя. Шаблон проверяется на побуждающие обороты (`guardrails.check_tone`).

### 8. Пересказ через LLM (`polish`)

Если LLM-слой включён и движок выбрал хотя бы одно вино, шаблонный текст переписывается живым языком.

LLM получает:

- системный промпт `SYSTEM_PROMPT.md`: факты только из переданных данных, при отсутствии признака — «в базе не указано»,
  тон информирующий, глубина объяснения по уровню гостя;
- уровень гостя (новичок, любитель, знаток);
- данные движка в JSON: `CANDIDATES` (название, роль, балл, неизвестные признаки, вклад каждого правила с весом
  и пояснением), `TYPE_FIT` (до 8 групп уместности типов), `CONTEXT` (разобранный запрос) и `CANDIDATES_FACTS`
  (категория, сорт, регион, винодельня, признаки и полное описание каждого выбранного вина);
- готовый шаблонный ответ с просьбой пересказать его, не меняя фактов и порядка вин.

Ответ LLM принимается, только если:

1. в нём названы **все** вина выдачи (сравнение по нормализованному названию);
2. нет побуждающих оборотов (тот же `check_tone`, что и для шаблонов);
3. нет цен (числа из 3–6 цифр с «руб» или «₽»).

Иначе, а также при сетевой ошибке, ошибке API или таймауте, остаётся шаблонный текст. Поля `picks`, `types`,
`context` в ответе API всегда приходят от движка. Нейтральная приписка («это справка по каталогу, а не совет пить…»)
добавляется кодом после LLM, поэтому модель её не пишет и не может убрать.

### 9. Диалог и обратная связь

- Сессия помнит контекст: новые уточнения дополняют прежние («а теперь без дуба»).
- «Не понравилось 2» исключает вино из выдачи в этой сессии; оценки пишутся в `media/sommelier/feedback.jsonl`
  как задел для калибровки весов, автоматически пока не используются.
- Сессии хранятся в памяти процесса (TTL 1 час, до 500 сессий), после перезапуска API начинаются заново.
  LLM-клиент один на процесс; своей памяти у него нет, историю диалога он получает только из контекста сессии.

### Пример: «утка с вишнёвым соусом»

Разбор: утка (интенсивность 3,0, жир 3,5) + ягодный соус (сладость 1,0, кислота 1,5, интенсивность +0,2)
→ интенсивность 3,2, жир 3,5, сладость 1,0; теги «птица», «утка», «сладко-кислый».

| № | Вино | Роль | Балл | Доводы |
|---|---|---|---|---|
| 1 | Alma Valley Пино Гри, белое полусухое | лучшее совпадение | 76,0 | вес совпал (+1,0); кислотность режет жир (+0,88); сладость не ниже блюда (+0,5) |
| 2 | Шато де Талю Каберне Фран Резерв, красное сухое | классический вариант | 75,3 | вес (+0,93); жир/кислота (+0,88); танины (+0,6); тёмные ягоды к соусу (+0,8); оговорка: вино суше блюда (−0,27) |
| 3 | Бастардо Кефесия, красное сухое | другой стиль | 75,3 | те же доводы, другой сорт |

С LLM состав, порядок и баллы этих трёх вин те же; меняется только формулировка текста.

## Сорта и типы вина: профиль и сравнение

Вопросы «расскажи про Саперави», «чем Мерло отличается от Каберне Совиньон», «чем красное отличается от белого»
обрабатываются без подбора.

1. **Группа.** Сорт — все вина каталога с этим сортом. Тип — по признакам: красное, белое, розовое, оранжевое
   (тихие), игристое, сладкое (сладость 2–3), сухое (сладость 0). При сравнении берутся два самых частых
   в каталоге сорта или типа из вопроса.
2. **Профиль группы** (`engine.group_profile`): число вин; средние тело, кислотность, танины и по скольким описаниям
   они посчитаны; доля описаний, где упомянуты танины; доли сухих, сладких, с дубом, игристых; 4 самых частых аромата
   и до 3 «отличительных» (встречаются в группе в 1,25 раза чаще, чем по каталогу, и не меньше чем у 3 вин или 15 % группы);
   3 главных региона; 3 категории блюд из описаний; 3 примера вин с самыми подробными описаниями.
3. **Шаблон** (`render_profile`, `render_profile_comparison`): профиль списком; при сравнении — признаки рядом
   и ароматы, доли которых различаются на 10 и более процентных пунктов. Если вин в группе меньше 10,
   добавляется предупреждение, что выводы ориентировочные.
4. **Пересказ через LLM** (`retell`). LLM получает шаблон как `GROUP_STATS`, единственный источник фактов,
   и пересказывает его: что это значит для вкуса и с чем такое вино обычно сочетается. Ответ принимается,
   только если в нём остались название каждой группы (сорт — дословно, тип — в любой падежной форме: «у красных вин»)
   и число вин, по которому сделан вывод, и нет побуждающих оборотов и цен. Иначе — шаблон.

В конце добавляется пометка «это справка по каталогу, а не призыв употреблять алкоголь».

## Общие вопросы о вине (только с LLM)

Если движок не нашёл в сообщении ни блюда, ни повода, ни пожеланий («что такое танины», «как хранить открытую бутылку»),
вопрос уходит в LLM (`answer`) с отдельным промптом:

- отвечать по-русски, коротко (до 8 предложений), по общеизвестным фактам о вине: термины, подача, хранение,
  температура, бокалы, сочетания в целом;
- **не называть конкретные вина, винодельни, бренды и цены** — за конкретикой предложить написать блюдо или повод,
  чтобы подбор сделал каталог;
- тот же тон и те же запреты, что в `guardrails.py`; на вопросы не о вине, еде и напитках — вежливо сказать,
  что это сомелье, и перечислить, с чем он помогает.

К запросу добавляется контекст сессии: блюдо гостя и названия вин последней выдачи. Ответ проверяется на побуждающие
обороты и цены; к нему добавляется пометка-справка (`kind=answer`). Если LLM выключена, ответила с ошибкой
или ответ не прошёл проверку, сомелье задаёт уточняющий вопрос (`kind=clarify`), как и раньше.

Это единственное место, где текст строится не на данных каталога, а на общих знаниях модели. Запрет называть
конкретные вина задан только в промпте, кодом он не проверяется.

## Вино → блюда

Точки входа без сессии, их вызывает сканер после распознавания этикетки:
`GET /api/sommelier/wine/{slug}` и `GET /api/sommelier/wine/{slug}/alternatives`. **LLM здесь не используется**:
справка строится только из карточки и правил движка.

Полного рейтинга блюд к вину нет: сомелье оценивает блюдо гостя и подсказывает несколько типовых блюд. Он показывает:

1. **Справку по вину** (`text`). Цвет, сладость, сорт, регион, винодельня, температура подачи, крепость, танины
   и кислотность словами, цитата из описания.
2. **Структурированную карточку** (`profile`, `explain.wine_profile`), которую сканер рисует блоками:
   - `sections` — фразы описания, разложенные по блокам «Цвет», «Аромат», «Вкус», «Гастрономия», «Технология»,
     «О вине». Фразы не переписываются, только группируются: предложение попадает в блок по первому найденному
     ключевому слову («аромат», «вкус», «сочетается», «выдержка»…), без ключевых слов — в блок предыдущего;
     метки вроде «Вкус:» в начале фразы убираются. Если о цвете в описании ничего нет, блок «Цвет» берётся из поля
     карточки;
   - `scales` — сладость, тело, танины, кислотность на шкале 0–1 со словесной оценкой; `null` — в базе не указано;
   - `aromas`, `foods` — группы ароматов и категории блюд из описания;
   - `facts` — температура подачи, крепость, выдержка, наличие дуба.
3. **«С чем подать».** Категории блюд, которые называет само описание вина (признак «блюда из описания»).
   Если описание о еде молчит, блок пустой.
4. **Оценку конкретного блюда** (`?dish=стейк рибай`). Блюдо гостя проходит тот же разбор и те же восемь правил,
   выводятся балл и доводы «за» и «против».
   Пример: Абрау-Дюрсо Пино Нуар со стейком рибай — 68,4/100; за: кислотность режет жир, сухое вино не теряется
   рядом с блюдом, пряные ноты дополняют мясо, описание само называет красное мясо; против: блюдо насыщенное,
   вино лёгкое.
5. **Инфографику сочетания** (`pairing`, `explain.pairing_profile`), которую сканер рисует вместо текста:
   - **вердикт по месту в каталоге.** Абсолютный балл у разных блюд несопоставим: к стейку лучшее вино каталога
     набирает 84, к утке с вишнёвым соусом — 76. Поэтому то же блюдо оценивается со всеми винами каталога
     (около 20 мс), и вердикт зависит от доли вин, которые набрали меньше:

     | Доля вин каталога с меньшим баллом | Вердикт |
     |---|---|
     | от 90 % | Отличная пара |
     | от 70 % | Хорошая пара |
     | от 40 % | Допустимо |
     | меньше 40 % | Не лучший выбор |

     Если правило сладости дало −0,6 и ниже (вино заметно суше блюда), вердикт всегда «Не лучший выбор»:
     это главный конфликт пары, так же поступает уместность типов вина;
   - **доводы «Что работает» / «Что мешает»** — те же вклады правил, что в тексте, с силой вклада
     (|v| · вес / 3,5) и цитатой из описания вина отдельной строкой;
   - **профиль блюда** — признаки из разбора: насыщенность, жирность, сладость, солёность, острота;
   - **«С чем это вино раскроется лучше»** — 4 блюда с наибольшим баллом из 28 типовых (`dishes.SUGGESTIONS`:
     стейк, утка, белая рыба, мягкий сыр, десерт…). Каждое проходит обычный разбор блюда; блюдо гостя
     не предлагается. Нажатие на блюдо в сканере оценивает новое сочетание.

   Пример: Абрау-Дюрсо Пино Нуар — со стейком рибай «Хорошая пара» (68,4; лучше 87 % каталога), с тирамису
   «Не лучший выбор» (48,5; вино суше десерта); лучше всего раскроется с мягким сыром (78), курицей (76),
   белой рыбой (75), пловом (74).
6. **Альтернативы** — похожие вина каталога.

### Алгоритм альтернатив

Обязательные условия: тот же цвет и игристость; сладость отличается не больше чем на одну ступень;
другое вино (не то же название той же винодельни).

| Совпадение | Баллы |
|---|---|
| тот же сорт | 0,35 |
| тот же тип (цвет + сладость) | 0,15 |
| близкое тело | до 0,15 |
| близкие танины | до 0,10 |
| близкая кислотность | до 0,05 |
| общие ароматы (доля пересечения) | до 0,20 |
| та же сладость | 0,05 |
| тот же регион | 0,10 |
| дуб у обоих | 0,05 |

«Близость» признака = max(0; 1 − \|разница\| / 2). Из одной винодельни берётся не больше двух вин,
одноимённые не повторяются. Каждый довод взят из полей карточки.

## Этические ограничения

`guardrails.py` отклоняет запросы, где упоминаются несовершеннолетие, беременность, вождение,
лекарства или зависимость, «напиться», «сколько выпить». Эта проверка идёт первой, до движка и до LLM:
такие сообщения в модель не отправляются. Отказ гостя от вина принимается без уговоров.

Каждый ответ — шаблонный или от LLM — проверяется на побуждающие обороты. Те же правила тона записаны
в промптах LLM, но решает проверка в коде: ответ модели с запрещённым оборотом отбрасывается. Нейтральная приписка
добавляется кодом в конце любого ответа с рекомендацией, справкой по вину, профилем или сравнением.

## LLM-слой: настройки и поведение

| Параметр | Значение |
|---|---|
| Включение | `GOOGLE_API_KEY` в `.env`; без ключа слой выключен, в лог при старте пишется «templates only» |
| Модель | `SOMMELIER_LLM_MODEL`, по умолчанию `gemini-flash-latest` |
| Таймаут | `SOMMELIER_LLM_TIMEOUT_SECONDS`, по умолчанию 20 с |
| Вызов | REST API Gemini (`generateContent`) стандартной библиотекой, без дополнительных пакетов |
| Температура | 0,3 |
| «Размышления» | для моделей не из семейства 2.x — `thinkingLevel: low`, к лимиту токенов добавляется запас 2000 |
| Лимит ответа | 1500 токенов для подбора, 1200 для профиля и сравнения, 800 для общего вопроса (плюс запас) |
| Повтор | один повтор при сетевой ошибке или таймауте; при ответе API с ошибкой — сразу шаблон |
| Задержка | около 5–10 с на ответ с подбором |

| Где | Метод | Что делает | Если не прошло |
|---|---|---|---|
| подбор к блюду | `polish` | пересказывает шаблонный ответ | шаблон |
| профиль, сравнение | `retell` | пересказывает статистику группы | шаблон |
| общий вопрос | `answer` | отвечает по общим знаниям, без конкретных вин | уточняющий вопрос |
| разбор запроса | `extract_context` | есть в коде, не подключён | — |
| вино с этикетки, альтернативы | — | LLM не вызывается | — |

## Ограничения

- Нет цен и наличия: бюджет фиксируется, но не применяется.
- Тело вина оценивается косвенно по словам описания — главный кандидат на ручную разметку.
- Веса правил заданы вручную и не откалиброваны на оценках сомелье-эксперта.
- Словари блюд и признаков — регулярные выражения по основам слов; редкие формулировки могут не распознаться.
  LLM здесь не помогает: разбор запроса идёт без неё.
- Блюда из карточки распознаются по 10 категориям: «BBQ», «брускетты», «кавказская кухня», «паштеты»
  в описании не попадают ни в одну.
- В обратную сторону (вино → блюда) полного рейтинга блюд нет: подсказка выбирает из 28 типовых блюд, и её состав
  определяют те же правила, что и подбор (например, Пино Нуар получает высокий балл и к плову).
- Если сомелье получает slug, которого нет в его CSV, он ищет вино по похожему названию и может показать
  справку о другом вине.
- Проверки LLM-ответа ловят пропущенные вина, побуждающий тон и цены, но не проверяют каждое утверждение
  о вкусе: неточный пересказ признака, который есть в данных, может пройти. Защита от этого — только системный промпт.
- В свободных ответах (`answer`) запрет называть конкретные вина и бренды не проверяется кодом.
- С включённым LLM-слоем текст запроса гостя, данные выбранных вин и контекст сессии отправляются во внешний API Google.
