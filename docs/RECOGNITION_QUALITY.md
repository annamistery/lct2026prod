# Качество распознавания: исследование и калибровка каскада

Документ описывает, как была измерена и улучшена точность распознавания, почему из решения убран OCR и как устроен ответ «Данного вина нет в каталоге». Все цифры воспроизводятся скриптами из `scripts/` (раздел 7).

## 1. Данные для проверки

| Набор | Фото | Вино в каталоге | Вина нет в каталоге | Разметка |
|---|---|---|---|---|
| `tmp/1` | 27 | 27 | 0 | `mapping.json` заказчика |
| `tmp/2` | 25 | 24 | 1 (slug из разметки отсутствует в каталоге) | `mapping.json` заказчика |
| «Реальные фото» | 119 | 77 (для 6 — два равноправных товара-дубля) | 35 | `labels.tsv`, ручная разметка по коллажам «фото + 6 кандидатов» и поиску по названиям каталога |
| Исключено из оценки | 7 | — | — | нечитаемое название или ошибка фото в каталоге (`status = unsure`) |

Итого **128 фото вин из каталога** и **36 фото вин, которых в каталоге нет**. Каталог распознавания — 2 017 вин, по 116 эталонных векторов на вино для каждой модели.

Дополнительно проверялся **смоделированный отказ**: у фото вина из каталога это вино убирается из поиска, а похожие вина той же винодельни остаются. Это самый трудный случай «нового вина из известной серии».

## 2. Что было

Прежний каскад: DINOv2 → если лидер неочевиден, SigLIP 2 выбирает среди ≤ 5 соседей от DINOv2 → опционально OCR.

- Точность top-1: **86,7 %** (111 из 128).
- Ответа «нет в каталоге» не было: на любое фото возвращалось ближайшее вино.

## 3. Что изменено в распознавании

Эксперименты на выгруженных векторах (`scripts/research_dump_features.py`) показали:

| Вариант | Top-1 |
|---|---|
| DINOv2, кроп в letterbox (как было в этапе 1) | 70,3 % |
| SigLIP 2 по всему каталогу, кроп с маской сегментации (как было в этапе 2) | 89,1 % |
| SigLIP 2 по всему каталогу, кроп в letterbox без маски | 93,0 % |
| **Слияние: SigLIP 2 (оба вида) + 0,3 · DINOv2 (оба вида)** | **95,3 %** |
| То же, кандидаты — 30 лучших по DINOv2 (итоговое решение) | **95,3 %** |

Причины прироста:

1. **Оба вида кропа.** Маска сегментации иногда отрезает часть этикетки, letterbox оставляет фон. Сумма оценок по двум видам устойчивее, чем любой из них.
2. **SigLIP 2 участвует всегда**, а не только среди 5 соседей: прежний отбор соседей по DINOv2 иногда отсекал верное вино.
3. **DINOv2 отбирает 30 кандидатов** (по усреднённому вектору двух видов верное вино входит в 30 лучших в 128 из 128 случаев). SigLIP 2 затем сравнивает только их — быстро, без полного перебора 234 тыс. векторов.

Все 6 оставшихся ошибок — «близнецы» той же винодельни, верное вино на 2-м месте. Часть из них — дубли в самом каталоге (раздел 6).

## 4. OCR: проверен и исключён

EasyOCR (ru + en) прочитал текст со всех 171 кропа. Проверялись два применения:

- **Переранжирование близких кандидатов** по совпадению отличительных слов названия: в лучшем случае +1 верный ответ из 128, при других весах OCR чаще ломал верные ответы, чем исправлял. При этом он добавлял около 1 с к каждому запросу и тяжёлую зависимость.
- **Отказ «нет в каталоге» по «чужим» словам на этикетке:** у 66 % правильно распознанных вин OCR тоже находит слова, которых нет в названии. Названия в каталоге непоследовательны (этикетка «Рислинг · Ркацители · Сибирьковый», в каталоге «Долина Дона Белое»), мешает транслитерация. Такое правило отказывало бы верным ответам.

Вывод: OCR не даёт прироста и в каскад не входит.

### 4.1. Проверка этикетки визуально-языковой моделью (29.09.2026)

Вместо OCR этикетку читает локальная VLM (Ollama, `qwen2.5vl:7b`): она возвращает производителя, название,
сорта, цвет и сладость, а не сырой текст. Прочитанное сравнивается со структурированной карточкой
(`app/sommelier/data/catalog.json`) пяти ближайших кандидатов, только для ответа «похоже»
(`app/pipelines/search/cascade/label_check.py`, включается `CASCADE_LABEL_CHECK=true`):

- решают только **отличительные** слова названия — те, которых нет у соседних кандидатов (Красная стрелка
  «Рубин» против «Пино Нуар»); латинские сорта переводятся словарём (Sauvignon → совиньон);
- противоречие по сорту засчитывается, только если сорта кандидата нет во всём тексте этикетки;
  по сладости — только между несоседними классами (модель часто читает «полусухое» как «сухое»);
- отказ по названию — только если модель прочитала название, и его нет ни у одного кандидата;
- переключение на другого кандидата — только того же производителя или с его названием на этикетке.

Результат на 118 размеченных фото «Реальные фото» (живой API, порог 0,55, кроп центральной бутылки):

| | без проверки | с проверкой |
|---|---|---|
| Вина из каталога, верный ответ | 71 / 77 | **72 / 77** |
| Вина не из каталога, ответ «нет в каталоге» | 29 / 41 | **35 / 41** |
| Всего верно | 100 / 118 | **107 / 118** |

Все 41 верный ответ «похоже» сохранились. Время ответа «похоже» на сервере: медиана 0,4 → 3,6 с (RTX 5080,
модель частично на CPU при соседстве с другими сервисами), максимум ≈ 10 с; «найдено» и «нет в каталоге»
не замедляются. Правила подбирались на этих же фото, поэтому цифры стоит перепроверить на новых снимках.

## 5. Ответ «Данного вина нет в каталоге»

Каскад отдаёт одну из трёх зон (`status` в ответе API). `similarity` — сходство SigLIP 2 лучшего кандидата, `margin` — отрыв его итоговой оценки от второго кандидата.

| Зона | Условие | Что показывается |
|---|---|---|
| `found` — «Вино найдено» | similarity ≥ 0,83 **и** margin ≥ 0,15 | вино, справка сомелье, альтернативы |
| `probable` — «Похоже на это вино» | всё остальное | лучший кандидат с просьбой сверить название, год и цвет; альтернативы |
| `not_in_catalog` — «Данного вина нет в каталоге» | similarity < 0,55 | `slug = null`; самые похожие этикетки каталога как «другие вина»; вопрос к сомелье |

Результат на всех размеченных фото (живой API, `scripts/eval_recognition.py`; замерен при прежнем пороге отказа 0,485):

| | найдено | похоже | нет в каталоге |
|---|---|---|---|
| 128 фото вин из каталога | 59 (**все 59 верны**) | 69 | **0** |
| 36 фото вин не из каталога | **0** | 15 | 21 |
| 128 смоделированных отказов | 5 | 110 | 13 |

**Порог отказа 0,55 (с 29.09.2026).** Прежний порог 0,485 лежал ниже сходства любого фото вина из каталога (минимум — 0,505), поэтому ответ «нет в каталоге» ни разу не был ошибочным. После ручной проверки 119 реальных фото порог поднят до 0,55: ложных совпадений «похоже» на винах не из каталога стало 10 из 39 вместо 19, а одно верное фото вина из каталога (сходство 0,505) теперь получает ответ «нет в каталоге». Ответ «найдено» по-прежнему ни разу не дан вину не из каталога.

**Чего гарантировать нельзя.** Стопроцентно отличить новое вино из известной серии (тот же дизайн, другой сорт или цвет: Alveus Ultra Cuvée «Оранж» при Brut в каталоге) по изображению невозможно ни одной моделью. Такие вина попадают в зону «похоже» — система не утверждает, что это вино из каталога, а просит сверить название. 5 «найдено» среди смоделированных отказов — пары с одинаковой картинкой в каталоге (раздел 6), то есть фактически то же вино.

Гарантия эмпирическая: она проверена на 164 фото. При изменении каталога или появлении новых размеченных фото пороги пересчитываются (`scripts/calibrate_cascade.py`).

## 6. Проблемы данных каталога

Они напрямую ограничивают точность и уверенность, их стоит исправить в первую очередь:

1. **Чужие фото у товаров.** У «Velvet Season» Мускат Оттонель и Рислинг (Фанагория) в каталоге фото Velvet Season Саперави и Каберне. У «Бастардо — Кефесия» (Валерий Захарьин) — фото «Авторское вино, Каберне Совиньон». Самое слабое верное распознавание (0,505), которое задаёт порог отказа, — как раз Velvet Season. После исправления фото порог можно поднять примерно до 0,53 и отклонять больше чужих вин (в эксперименте — 24 из 36 вместо 21).
2. **42 пары товаров с одинаковой картинкой** (`scripts/audit_catalog.py`): одно вино загружено дважды («Мускат» и «Бельбек Мускат», «Алиготе Авторское» и «Алиготе. Авторское вино»), разные года одного вина или ошибочная общая картинка («Новый Свет полусладкое» и «Новый Свет выдержанное брют»). По фото такие пары не различить: дубли нужно объединить, фото — заменить.

## 7. Как воспроизвести

```bash
# 1. Векторы каталога и тестовых фото (в контейнере API, GPU + БД) -> media/research/
docker compose exec api python scripts/research_dump_features.py \
    --sets tmp1=/srv/app/tmp/1 tmp2=/srv/app/tmp/2 real=/media/research/real

# 2. Калибровка порогов и точность без GPU (повторяет каскад на выгруженных векторах)
python scripts/calibrate_cascade.py media/research

# 3. Проверка живого сервиса по разметке (mapping.json / labels.tsv)
python scripts/eval_recognition.py --api http://127.0.0.1:8030 \
    --sets tmp1=tmp/1 tmp2=tmp/2 "real=/путь/к/Реальные фото"

# 4. Аудит каталога: пары товаров с одинаковой этикеткой -> media/artifacts/catalog_audit.tsv
docker compose exec api python scripts/audit_catalog.py
```

Фото «Реальные фото» и их разметка (`labels.tsv`) — данные заказчика, в Git не хранятся. Для шага 1 их нужно положить в `media/research/real/` вместе с `labels.tsv`.

## 8. Что улучшит точность дальше

1. **Исправить каталог** (раздел 6) — самый дешёвый прирост точности и уверенности.
2. **Добавить реальные фото как эталоны.** Таблицы эмбеддингов уже поддерживают `sample_type = real / customer`. Фото из магазинов с подтверждённым вином дают модели «живые» примеры и сдвигают сходство верных ответов вверх — зона «похоже» сужается.
3. **Дообучить SigLIP 2 на «близнецах»** (hard negatives: вина одной серии), чтобы увеличить отрыв верного вина от соседа.
4. **Расширить размеченную выборку** до нескольких сотен фото — пороги станут надёжнее, а зону «найдено» можно будет расширить без потери точности.
